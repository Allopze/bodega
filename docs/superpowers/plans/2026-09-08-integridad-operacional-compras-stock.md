# Integridad Operacional de Compras y Stock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Incorporar conciliación N:N de líneas documentales, disponibilidad proyectada informativa y expedientes verificables de integridad para compras, recepción y stock.

**Architecture:** Dos módulos profundos conservan las reglas de asignación documental y disponibilidad dentro de sus dominios. Un tercer módulo ofrece una interfaz pequeña para persistir y verificar hallazgos producidos por detectores de dominio, sin convertirse en motor configurable ni modificar automáticamente los datos observados.

**Tech Stack:** Next.js App Router, React 19, TypeScript, Drizzle ORM, PostgreSQL 16, Vitest/PGlite, Playwright y componentes compartidos de Bodega.

**Spec:** `docs/superpowers/specs/2026-09-08-integridad-operacional-compras-stock-design.md`

**Benchmark source:** `docs/audits/COMPARATIVA_ODOO_ERPNEXT_BODEGA_2026-09-07.md` (piloto A, prioridades P0).

## Global Constraints

- Odoo y ERPNext son sólo referencias de diseño; no se agregan dependencias, sincronizaciones ni runtimes externos.
- `lib/` + `app/` siguen siendo la fuente de verdad; no se recrean servicios bajo `modules/` ni `core/`.
- `worksite_stock.quantity` sigue siendo el único saldo físico persistido y `applyMovementTx` el único camino de mutación de stock.
- La proyección es informativa y nunca bloquea solicitudes, OC, recepciones o entregas.
- Toda identidad visible conserva producto, SKU, talla, color, medida, modelo y demás atributos concretos disponibles.
- Solicitudes, OC, líneas y entregas terminales/anuladas no generan demanda ni alertas activas.
- Toda lectura y acción intersecta permisos con scope de faena; un ID válido fuera de scope se trata como inexistente.
- Server Actions son entradas públicas: autenticar, autorizar, validar `FormData` y releer ownership/estado desde PostgreSQL.
- No se exponen snapshots completos a Client Components; sólo DTO redactado.
- Migraciones se generan desde schema; no editar a mano `meta/_journal.json` ni migraciones previas.
- La UI reutiliza `PageHeader`, `PageContainer`, tablas, filtros y estados compartidos; no agrega un buscador de texto duplicado.
- Exportaciones siguen siendo exclusivamente XLSX.
- Las verificaciones pesadas se ejecutan secuencialmente mediante el resource guard.
- A fecha de este plan, `package.json` no expone `audit`, `audit:full` ni
  `audit:report`; no se deben inventar. La auditoría completa queda como gate
  pendiente hasta restaurar explícitamente el harness en un trabajo separado.
- El artefacto preexistente `AUDITORIA_TALLAS_EPP_2026-09-08.md` queda fuera de todos los commits.

## Final release decision

La entrega sólo es candidata a release cuando Tasks 1–7 están completas, el
preflight devuelve cero inconsistencias estructurales, la concurrencia corrió
contra PostgreSQL real y cualquier brecha queda descrita. Si `audit:full` está
disponible, `qa/reports/latest.md` debe haberse leído; si sigue ausente, la
decisión de release debe aceptar explícitamente esa brecha o esperar la
restauración del harness. Una build local o un flujo agregado verde no equivalen
a despliegue ni a UAT de producción.
